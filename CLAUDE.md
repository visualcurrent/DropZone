# Project: DropZone — instant LAN file sharing where only the host installs anything

Doc tier: 3

## Goal
A host runs one pure-stdlib Python file; everyone else on the same WiFi opens a browser (via a QR code) to upload and download files — no app, no account, any OS. A correct result: on a phone hosting through the Android app, multi-GB files upload and download byte-exact without freezing, server memory stays flat, and each file downloads exactly once (no OS-suffixed `name (1).ext` duplicates).

## Environment
- Python 3.6+ standard library only — zero third-party packages. A hard rule; a backlog item must explicitly approve any dependency. [verified: README + docs/DEVELOPMENT.md]
- Runs on Windows/macOS/Linux and on Android through the app (`android\`). Termux is a test bench only, never a target (Gabe, 2026-11-12). Host page `http://localhost:7070`, remote page `http://<ip>:7070/remote`. Port and the four transfer limits are constants near the top of `DropZone.py`.
- Tests are dependency-free and start the real server over sockets: `python3 tests/run_all.py`. The memory checks read `/proc/<pid>/status`, so they measure memory only on Linux/Termux, not Windows/macOS. [verified: tests/README.md]
- Refreshing the Termux test bench: Gabe downloads the new `DropZone.py` from GitHub by hand after a push; no rename, no Syncthing, no widget. The version constant, not the filename, identifies the running build. [verified: Gabe, 2026-11-11 — replaces the earlier Syncthing/Termux:Widget line, which was wrong]
- Android app (`android\`): `android\build.bat` (Windows) copies the current `DropZone.py` into the app and writes `android\DropZone-debug.apk`; installing that APK over the old one is the only way a phone gets a new core. Version name reads `<wrapper>-dz<core>`, e.g. `0.1.02-dz0.2.15`. Toolchain is one portable folder, `D:\AndroidToolchain` (JDK 17, Gradle 8.14.3, Android SDK 35, emulator); removal in `UNINSTALL.md`. Pins: Android Gradle plugin 8.13.2, Chaquopy 17.2.0 (Python 3.13 in the APK; the PC needs its own Python 3.13 to build), minSdk 26, targetSdk 35, ABIs arm64-v8a + x86_64. App id `com.visualcurrent.dropzone`; on the phone the log is `files/DropZone.log` (`adb shell run-as com.visualcurrent.dropzone cat files/DropZone.log`). Use `C:\adb\adb.exe` only; mixing it with the toolchain's `adb.exe` restarts the adb server and drops connections.
- DropCast (`android\dropcast\`) packages the same Python folder as DropZone's app plus its own `dc_host.py` and `dc_qr.py`; build it alone with Gradle task `:dropcast:assembleDebug` (same toolchain variables as `build.bat`), output `android\DropCast-debug.apk`, version `<cast>-dz<core>`. Its logs on the phone are `files/DropCast.log` (app) and `files/DropZone.log` (server) under `com.visualcurrent.dropcast`. [verified: builds and phone runs 2026-11-13]
- The tests' harness is Linux-only (`os.setsid`); this PC has no WSL. On Windows they run only through a scratch shim that swaps the harness's launch/stop, and `test_zip_streaming.py` cannot run there at all (it deletes a file it still has open).

## Do-not-re-derive (verified findings)
- Upload-freeze cause: `do_POST` read the whole request body into RAM (`self.rfile.read(length)`) and `parse_multipart` copied it again, so peak RSS was ~2–3× file size and the phone OOM-killed large uploads. Fixed v0.2.05 by streaming the body to disk in `UPLOAD_CHUNK` (4 MB) blocks. [verified: v0.2.04 field-log RSS table; field-confirmed closed v0.2.09 — 2.4/2.6/1.8 GB singles + 4.4 GB batch byte-exact, RSS flat 12–16 MB]
- Small-file duplicate downloads were caused by advertising `Accept-Ranges`, which makes Chrome start/cancel/re-segment a download (a small file finishes the first attempt before the cancel → saved twice; a large file is cancelled → one file). Fixed v0.2.14 by NOT advertising `Accept-Ranges`; an explicit `Range` request is still honored with 206. [verified: docs/commits/0016 + tests/test_download_range.py]
- The app shell must be served `Cache-Control: no-store`; the page inlines all CSS/JS, so without it browsers pin an old client across deploys (why the v0.2.11 client fix appeared not to work until v0.2.12). [verified: v0.2.11/0.2.12 field logs]
- The blob / in-page download (`blobSave`, v0.2.13) deduped but had unacceptable UX (buffered the whole file, no feedback, stacked save dialogs); REVERTED in v0.2.14 — do not resurrect. [verified: v0.2.13 log + revert note in docs/commits/0016]
- A response header can only carry latin-1 text (`http.server` limit). A raw filename in `Content-Disposition` killed single-file downloads of names with an emoji or a curly apostrophe while the zip worked. Fixed v0.2.15: ASCII stand-in in the quoted `filename=""`, real name in `filename*=UTF-8''`. [verified: 9 tracebacks in the app's log 2026-11-11; `tests/test_download_filename.py`]
- Android: `LOG_FILE`, `UPLOAD_DIR` and `LOCAL_IP` are read at call time, so `dz_host.py` replaces them after `import DropZone` and the core needs no edit. [verified: emulator + phone runs 2026-11-11, log and uploads land in the app's `files` folder]
- Android: foreground-service type `connectedDevice` with `CHANGE_WIFI_STATE` starts cleanly on Android 15 and 16. [verified: `dumpsys activity services` shows `isForeground=true types=0x10` on both]
- Android: a foreground service and a wake lock do not stop a phone maker's freezer. On the Xiaomi (HyperOS, Android 16) the app was frozen for 3.5 min with the screen on (`reason: greeze`); requests then hang, they do not fail, and all run at the thaw. An empty stretch in `DropZone.log` followed by a burst is the signature; check `dumpsys greezer` and logcat for `disabled: true` before suspecting the server. Cure: App info > Power > No restrictions, which also sets Android's battery exemption, so the app detects it with `isIgnoringBatteryOptimizations` and shows a notice until it is set. [verified: logcat + greezer history 2026-11-11; 34 transfers with no freeze after the setting]
- Android: install over adb with `adb install --user 0 -r <apk>`. Without `--user 0` the APK goes into every user profile on the phone; on the Samsung (SM-S921B) that includes the dual-app profile, user 95, which shows as a second DropZone with its own storage and its own `files/DropZone.log` (`run-as com.visualcurrent.dropzone --user 95 cat files/DropZone.log`). [verified: `pm list users`, `dumpsys package`, both logs read 2026-11-15]
- Android: the newest command-line tools release (`commandlinetools-win-16111833`) only bootstraps a second download, which failed here with a socket-permission error; release `13114758` has the classic `sdkmanager` and works. [verified: both tried 2026-11-11]
- Android: the phone maker's freezer exemption is per app. DropCast, a new app id, was frozen in the background (guests' pages hung, then all ran at the thaw) until its own battery option was set; opening a QR on the host phone itself is what sends the app to the background. Each app shows its notice until `isIgnoringBatteryOptimizations` is true. [verified: `dumpsys greezer`, logcat and server log 2026-11-13; no freeze after the setting]
- Android: a page inside an app (WebView) takes light or dark from the APP's theme, not the phone's setting; DropCast's theme is `Theme.DeviceDefault.DayNight` on Android 10+ for that reason. [verified: Gabe's phone, before and after, 2026-11-13]
- Android: a photo read through the media store without the media-location permission arrives the same size with 56 bytes blanked near its start, so it is not byte-identical to the original; a video is untouched. Use a video or a non-media file for byte-exact checks. [verified: `cmp` 2026-11-13; that the bytes are the GPS location is est_]
- Android: the system rebuilds a screen on rotation or theme change and hands back the same share request; take a shared file only when `savedInstanceState` is null. A share faked from adb needs the file's address as the intent's data with `--grant-read-uri-permission`; on the extra alone it is refused. [verified: phone runs 2026-11-13]
