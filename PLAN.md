## M2 — DropCast (single-file share app)
A second, simpler app for people who will never manage a DropZone session: share one file, a QR appears, anyone on the WiFi scans it and downloads. Requested by Gabe 2026-11-13; planned to fold into DropZone as a feature once it works. Built from the same `android\` tree and the same unedited `DropZone.py`; the DropCast pages and routes live in an add-on file beside `dz_host.py`. PROPOSED — awaiting Gabe's sign-off; nothing is built.
**Agreed behaviour (Gabe, 2026-11-13):**
- Two ways in: share one file to DropCast from any file manager, or open DropCast and tap "Choose a file". Both lead to the same screen. One file per share; no zip, no lists, no names.
- The file is copied into the app's storage (as DropZone does), with visible "Preparing" progress, then the host's screen shows thumbnail or icon, filename and QR.
- Guest page (from the QR): a short friendly note; a frame holding the thumbnail or icon, the filename and a Download button; below it a "Share a file" button. Sharing uploads to the host's phone with real progress (animated), then shows the guest a QR for that file.
- Every share makes a new file + QR pair. All pairs keep working until Stop. A file identical to one already held (MD5 match) reuses the existing pair instead of making a new one.
- Host's screen shows a QR only for files the host sent. A received file shows as a card, "This file has been shared — Download"; Download opens Android's save dialog and copies the file out of the app.
- Stop is manual and deletes everything the app holds. If received files are unsaved, Stop asks first ("You have N unsaved files. Stop anyway?").
- The host's screen is a web page shown inside the app (WebView), so host and guest share one design and one QR library (`qrcodejs`, embedded in the page; no internet needed). This reverses, for DropCast only, the M1 item "Host page inside the app — deferred".

## Done / dropped (record — do not re-derive)
- [x] **1. Upload freeze on large files** — CLOSED field-confirmed v0.2.09. Cause: whole body read into RAM + `parse_multipart` copy → ~2–3× RSS → phone OOM. Fix v0.2.05 `stream_multipart()` (socket → disk in `UPLOAD_CHUNK`). Field: 2.4/2.6/1.8 GB singles + 4.4 GB batch byte-exact, RSS flat 12–16 MB, no freeze/OOM/traceback. Raw evidence in `_archive/DropZone.log` and `_archive/upload-freeze-log.md`.
- [x] **3. Version constant + show it on the host page** — shipped v0.2.01 (`__version__` + `VERSION_STAGE`; header + startup banner show the running build).
- [x] **9. Real upload progress bar** — shipped v0.2.05 (`XMLHttpRequest` `upload.onprogress`, true bytes + ETA; halts at a stall) replacing the fake `setInterval` timer.
- [x] **10. Duplicate / double downloads** — resolved v0.2.14. Root cause: advertising `Accept-Ranges` (added v0.2.10 for Safari) made Chrome start/cancel/re-segment; small files saved twice. Journey: v0.2.10 Range support; v0.2.11 anchor debounce; v0.2.12 `no-store` shell (so client fixes actually deploy); v0.2.13 blob (deduped but bad UX — REVERTED); v0.2.14 stop advertising `Accept-Ranges` (one plain native download; explicit `Range` still 206). Marked `[~]` in the old backlog pending the Android/iPhone field eyeball; tracked in M0 gate + SESSION.
- [x] **16. Single-file download fails for non-latin-1 filenames** — shipped v0.2.15. Cause: raw name in the `Content-Disposition` header, which `http.server` can only send as latin-1 → `UnicodeEncodeError`, no response; zip unaffected. Fix: ASCII stand-in in the quoted `filename=""`, real name in `filename*=UTF-8''`. Found in the field on the Android app 2026-11-11 (9 tracebacks in its log). Test: `tests/test_download_filename.py`.
- [-] **5. Long combined file list cannot scroll** — dropped, not reproducible; re-tested clean at 1100 files. Reopen only with a concrete repro.
- [-] **12. Light/dark theme regression** — dropped, external cause: a browser setting forcing night mode on the device, not a DropZone defect (code measured correct in headless Chromium). Between-session theme persistence is intentionally not wanted.
- [x] **13. Stream "download everything" as it is built** — shipped v0.2.09. Hand-rolled uniform-zip64 STORE streamer with an exact-size formula: TTFB ~1 ms (was tens of seconds), no temp file, real progress bar, flat memory; byte-exact incl. >4 GiB. Design + evidence in `_archive/streaming-zip-findings.md`; contract in ARCHITECTURE.
