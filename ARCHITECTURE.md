As-built structure. Update when a layer lands or a contract changes.

## Data flow
Guest browser -> `POST /api/session` (gets a sid + friendly name) -> uploads via `XMLHttpRequest` to `/api/upload` (real progress from `upload.onprogress`); the server streams the multipart body to a temp file and keeps only metadata (name/size/path) in RAM. Every page polls `/api/state` each second for the file list (grouped by user, own section pinned to the bottom) and the host-activity banner. Downloads: single files via `/api/download` (plain 200, native browser UI); bulk via `/api/download_all` (one user) and `/api/download_everything` (everyone else, foldered per user), streamed as built. Uploads live on disk in a temp folder cleared on Ctrl+C; state is in-memory and clears on restart.

## Contracts to preserve (break silently if drifted)
1. `/api/download` must NOT advertise `Accept-Ranges` on its 200/206 responses. It looks like a missing header; it is deliberate — advertising it makes Chrome start/cancel/re-segment and duplicates small files. The 416 branch keeps its own `Accept-Ranges` (range-specific, rarely hit, harmless).
2. `send_html` must stay `Cache-Control: no-store` (+ `Pragma`/`Expires`). The page inlines all CSS/JS; without it browsers pin an old client across deploys.
3. The Range apparatus (`parse_range`, the 206/416 branch, `ETag`, `Last-Modified`, `If-Range`) is reached only on an explicit `Range:` header (iOS Safari probe + resume). Keep it whole or remove it wholesale — never half-remove.
4. Bulk-zip byte layout is uniform zip64 so the length is a closed form; `zip_stream` output bytes MUST equal `zip_stream_size(entries)` exactly. A one-byte error breaks the transfer. Covered by `tests/test_zip_streaming.py`. The closed form: per file `= 30 + name + 20 + size + 24 + 46 + name + 28` (i.e. `size + 2*name + 148`); end `= 56 + 20 + 22` (i.e. `98`).
5. The upload path (`uploadFiles` client, `stream_multipart` / `do_POST` server) is memory-bounded and untouched since the upload-freeze fix — peak RSS must not scale with upload size. Covered by `tests/test_upload_memory.py`.
6. The `/api/state` `transfers` list drives the activity banner (queued / preparing / sending + queue position); every page polls it each second. Covered by `tests/test_queue_feedback.py`.
7. The Android wrapper `android\app\src\main\python\dz_host.py` uses these core names directly: `LOG_FILE`, `UPLOAD_DIR`, `LOCAL_IP` (replaced after import, so they must stay module variables read at call time, not captured into other objects at import), `get_local_ip`, `make_server`, `log`, `state_lock`, `shared_files`, `users`, `PORT`, `__version__`, `VERSION_STAGE`. The module must also stay importable without starting the server (everything that runs it sits under `if __name__ == "__main__"`). Renaming or restructuring any of these leaves Termux working and breaks the app at Start. NOT yet covered by a test (PLAN.md > M1 open items). DropCast's `android\dropcast\src\main\python\dc_host.py` adds to that list: `get_or_create_user`, `fmt_size`, `Handler.send_json`, `Handler.get_session` and the `session` cookie set by `POST /api/session`, the reply shape of `POST /api/upload` (`{"ok", "files": [{"id", "name", "size_str"}]}`) and its acceptance of a form field named `file`, the upload code reading the request body only through `self.rfile.read(n)` (DropCast swaps `self.rfile` for a counting reader during `/api/upload`; a `readline` or `readinto` there would go uncounted), `Handler` (subclassed, and replaced as a module variable before `make_server` runs, so `make_server` must keep looking the name up at call time), `CSS` and `LOGO_SVG` (reused in DropCast's pages; the pages rely on the colour variables `--bg --surf2 --off --border --div --txt --muted --hint --pri --pri-h --sh --r --rx --rfull`), the thumbnail slot `<tmp_path>.t` with the entry's `thumb` flag, and the shape of a file entry — it writes entries into `shared_files` and a user's `files` list itself, with the fields the upload route writes (`id`, `name`, `tmp_path`, `size`, `size_str`, `owner_id`, `owner_name`) plus its own `md5`. `/api/download` must keep serving any entry by its `tmp_path`.
8. Response header text must be latin-1 encodable (`http.server` limit): never put a raw user-supplied string (a filename, a display name) into `send_header`. Covered for `/api/download` by `tests/test_download_filename.py`.
9. In the Android app, state outlives a Stop: the Python interpreter lives as long as the app process, so `dz_host.stop()` clears `shared_files` and `users` and deletes the uploads itself. Core state added later that must not survive a restart needs clearing there too.
10. A thumbnail is bytes supplied by a guest. `GET /api/thumb` must keep its fixed `Content-Type: image/jpeg` and `X-Content-Type-Options: nosniff`, and `POST /api/thumb` must keep its three checks in this order: the poster owns the file, the size is within `THUMB_MAX_BYTES` before the body is kept, the bytes start with the JPEG signature. The thumbnail is stored as the upload's path plus `.t`, so anything that deletes an upload must delete that too, and the zip routes must keep reading only each file's own path. Covered by `tests/test_thumb.py`.
11. Stacking order on the page: header `.hdr` 100, preview `#peek` 110, activity banner `#activity` 120. The preview must cover the header and the banner must stay readable over the preview. The preview's close goes through the browser history (`closePeek` calls `history.back()`, the `popstate` listener calls `peekShut`), so anything else on the page that later uses `pushState` or `popstate` must leave the `{peek:1}` entry alone. Stars are page-only: `/api/download_starred` takes the ids in its address and the host keeps nothing.

## Streaming-zip design (v0.2.09)
A hand-rolled STORE streamer (`zip_stream` / `zip_stream_size`), chosen over predicting `zipfile`'s per-field zip64 decisions (it decides zip64 per field by actual value). Uniformly zip64: every file gets 8-byte size/offset fields and a data descriptor, and the archive always ends with a zip64 EOCD + locator + EOCD, so the byte layout is fixed and the exact size is a closed form (above) — the browser keeps a real progress bar, not a spinner. Uniform zip64 costs ~148 bytes/file regardless of size — negligible. Verified byte-exact including a 5 GiB single file past the 4 GiB boundary; archives pass `zipfile.testzip()` and Info-ZIP `unzip -t` and extract byte-exact; time-to-first-byte ~1 ms; peak RSS ~30 MB for a 364 MB archive; mid-stream cancel logs cleanly. Full evidence: `_archive/streaming-zip-findings.md`.
